## Порядок

1. Зафиксировать время, HEAD, грязные файлы, способ получения данных и их хеш. Сначала сопоставить с пакетом исходного отчёта. После принятых исправлений различия ожидаемы: исходный пакет служит историческим основанием, а проверяется текущая принятая версия. Не смешивать main с непринятым кандидатом. Если различия есть — явно сопоставить версии, не переносить старые выводы без проверки.
2. Для каждого урока составить карту: цель → где объяснена → какие слова введены → какие задания её проверяют → доступная помощь → ответ/проверка. Различать словарь, грамматику, базовые фразы, подсказки, явное введение нового и повторение ранее изученного.
3. Для каждого пункта исходного отчёта 1–23 сохранить исторический вердикт из принятого results/pilot-01-05-review.md и отдельно определить состояние на новой базе: исправлен с доказательством; остался; регрессировал; предложение; не проверен. Не повторять завершённую историческую сверку без новых оснований. Новые цитаты брать из проверяемой версии буквально. Не склеивать несколько фраз в цитату. Индекс, JSON-путь и строка кода должны совпадать с данными. Несовпадение цитаты указывается отдельно от верности основной проблемы.
4. Для каждого дефекта проследить потребителя данных: что видит ученик до ответа/после ответа; что используется ИИ; что скрыто; что является мёртвым кодом. Наличие поля не доказывает его использование. Проверить адаптацию пола говорящего и адресата раздельно.
5. Проверить реальные правила механики: ключ, варианты, кратность одинаковых плашек, допустимые ответы, нормализация, подсказки, оценивание, переход и повтор. Для языковой правки показать, что преобразование в коде не отменит её.
6. Спорные языковые нормы сверять по действительно открытой конкретной статье Академии, словарной статье или грамматике. Записать точную ссылку, какой вывод она поддерживает и какой не поддерживает. Не выдумывать просмотр источника, звук или измеренную уверенность.
7. Выполнить независимый поиск пропусков по всей карте покрытия. Не останавливаться на прежних 23 пунктах. Отдельно проверить утечку ответа в аудировании, подсказки первого шага ИИ, согласованность целей/образцов/условий завершения и обработку транскрипции.

## Формат результата

`project-control/results/pilot-01-05-v2-result.md` и рядом JSON с пунктами:

`id`, `originalIssueId` (если есть), `lessonId`, `mechanic`, `sourceCommit`, `sourcePath`, `jsonPath`, `exactSource`, `sourceHash`, `claim`, `evidence`, `counterEvidence`, `verdict`, `historicalVerdict`, `currentState`, `severityReason`, `proposedChange`, `affectedConsumers`, `verification`, `unverified`.

У каждого доказательства: способ проверки, точный файл результата, команда/шаги, фактический результат и границы. Для источника нормы: конкретная статья/страница, ссылка, поддерживаемый вывод и отметка «прочитано в этом аудите» либо ссылка на ранее зафиксированное доказательство архитектора. Наличие ссылки не равно прочтению. Хеш указывает, что именно хешировалось: байты исходного файла или конкретный снимок; не называть хешом файла хеш пересобранного объекта.

Вердикты: подтверждено; частично; опровергнуто; предложение; недостаточно оснований. Приоритет обосновывать последствиями для ученика, а не словами «100%». Доказанная опечатка, предпочтение оформления и риск прохождения имеют разный вес.

Для каждого из пяти уроков дать краткий итог и все непроверенные области. Отдельно — таблицу покрытия механизмов и цели без практики. Аудио и живые ответы ИИ проверять только при фактическом запуске; иначе оставить явно непроверенными. Нельзя считать статическую языковую сверку полной приёмкой урока.

- Каждое предлагаемое изменение имеет учебную цель и список затронутых потребителей. Непроверенное не представлено как выполненное.

## Проверки должны обнаруживать нарушение требования

- Проверка поведения вызывает настоящий компонент/обработчик. Присвоить correctAnswer переменной и сравнить её с собой — не проверить ответ ученика.
- Отрицательный запуск: те же новые ожидания, фактические исходные модули старого коммита, ожидаемое падение с ненулевым кодом. Отдельный всегда зелёный тест, ищущий старые ошибочные строки, этим не является.
- Сравнение с базой проверяет полные объекты в заявленной области. Количество записей или assert.ok(scenario) подтверждает только наличие. Если сравнивались уроки 6–10, нельзя написать «6–100 совпали».
- DOM-проверка фиксирует обратную связь после неверного ответа, повтор и успешный ответ. Одна видимая кнопка перехода не доказывает правильность.
- Заглушки и глобальное состояние очищаются и после падения. В отчёте отдельно указывать, что проверяет guard: дескрипторы globals, env, изменённые exports, require.cache; не расширять его фактический охват на словах.
- Для маленьких правок использовать достаточное доказательство без добавления тестов ради количества. Полную матрицу покрытия языковых материалов не заменять числом технических тестов.
