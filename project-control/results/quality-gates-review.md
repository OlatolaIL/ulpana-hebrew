## Почему одного workflow недостаточно

Required status checks должны быть настроены для защищаемой ветки и относиться к нужному SHA. Существующий YAML или успешный локальный тест сам по себе не запрещает слияние. Это соответствует [описанию защищённых веток GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) и [правилам проверки последнего SHA](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks). Требуется отдельно доказать применимость ограничения к принятому способу выпуска; защита main не доказывает отсутствие обходного deployment.

## Секреты: подтверждённый открытый вопрос

Ранее отмеченный в RELEASE_READINESS.md GitHub PAT всё ещё присутствует в URL локального remote. Диагностический вывод архитектора ошибочно отобразил URL с токеном в текущей сессии; значение здесь не повторяется. API принял авторизацию этим credential. Следовательно, прежнее требование замены/отзыва нельзя считать исполненным. Полученные permissions репозитория не доказывают все scopes токена; один endpoint вернул 403.

Нужно через штатное управление GitHub заменить и отозвать раскрытый credential, затем хранить доступ штатным credential helper и убрать секрет из remote URL. Отзыв не выполнялся: он изменит действующий доступ пользователя, а размещать/создавать новый постоянный секрет без отдельного согласованного шага нельзя. Проверка старого Groq-ключа из истории не выполнялась; его статус остаётся прежним, неподтверждённым. Не выводить git remote -v и не сохранять полные credential-bearing URLs в отчёты.
